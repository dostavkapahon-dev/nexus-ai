# CHANGELOG — NEXUS AI

## [Не влито] ветка `claude/social-media-automation-4gz8k0` — PR #41

### Убрана зависимость от Ayrshare
- Удалён `publishers/ayrshare_pub.py` — сторонний платный посредник, от доступности
  которого зависели и публикация, и аналитика.
- Публикация переведена на нативные API площадок: Instagram (Graph API), TikTok
  (Content Posting API), YouTube (Data API), VK, Threads, Telegram — с браузерным фолбэком.
- Аналитика переведена в новый `core/social_intel.py` с сохранением интерфейса
  (`is_configured`, `get_account_intelligence`).

### Публикация и анализ без API
- `core/server_browser.py` — браузер на стороне сервера (Playwright): те же команды,
  что у десктоп-агента, работает **без ПК пользователя**.
- Удалённый облачный браузер по CDP (`NEXUS_BROWSER_CDP`) — Chromium не поднимается
  на самом инстансе, Render остаётся лёгким.
- `core/browser_reader.py` — чтение профилей и постов через браузер, без ключей.
- Режимы `NEXUS_PUBLISH_MODE` и `NEXUS_ANALYZE_MODE`: `auto` / `browser` / `api`.

### Чтение соцсетей через официальные API
- `core/instagram_reader.py` — свой аккаунт с инсайтами (охват, просмотры, сохранения,
  репосты) + конкуренты через Business Discovery.
- `core/youtube_reader.py` — канал, подписчики, видео со статистикой (Data API v3).

### Единый пульт управления
- `core/command_center.py` — одна точка входа для дашборда и Telegram, общая лента
  событий, зеркалирование результатов в Telegram.
- `api/routes_control.py` — `POST /api/control/command`, `GET /api/control/feed`.
- Карточка «Пульт управления» на странице Центра в дашборде.

### Анализ из самого агента
- Инструмент `analyze` у оркестратора (`marketing_director`): досье аккаунта
  (instagram/tiktok/youtube) или разбор ролика по ссылке.
- Системный промпт требует вызывать `analyze` перед созданием контента.

### Безопасность
- SSRF-guard `server_browser.url_allowed`: блокируются loopback, приватные подсети,
  link-local и хосты облачных метаданных; разрешены только внешние http(s).
- Санитизация ников в `browser_reader` и в `instagram_reader.analyze_competitor`
  (username идёт в field-выражение Graph API).

### Деплой
- `Dockerfile` + `docker-compose.yml` (мультиарх, ffmpeg, Chromium, том `/data`).
- `DEPLOY_ORACLE.md` — инструкция для 24/7-хостинга.
- `render.yaml` — новые переменные публикации и анализа; лёгкая сборка без Chromium
  (браузер удалённый).

### BLOCK 09 — конвейер контента
- `content_factory._flush_steps()` переносит шаги конвейера в журнал задачи: раньше
  `report["steps"]` жил только в ответе, и по упавшей фабрике нельзя было понять,
  на каком шаге она сломалась. Журналирование идёт пачками в четырёх контрольных
  точках (до дорогой генерации, после медиа, после видео, после публикации),
  без повторов и без риска уронить конвейер.
- Точка согласования стала явным шагом `approval_requested`, а задача, упёршаяся
  в аппрув человека, получает статус **WAITING**, а не COMPLETED — раньше система
  сообщала «готово» о неопубликованном контенте.
- `POST /api/automation/factory` теперь создаёт Task и возвращает `task_id`:
  ручной запуск из дашборда оставляет такой же след, как ночной джоб.
- `run_daily_factory` возвращает отчёт наверх, чтобы планировщик видел WAITING.

### BLOCK 10 — движок публикации
- `core/publish_queue.py` — очередь публикаций в БД: текст, картинка, попытки, время
  следующей попытки. Раньше публикация была одноразовой: таймаут площадки означал
  потерянный пост — оставалась строка `failed` без текста, повторить её было нечем.
- Повторы с растущей паузой (2 → 8 → 30 → 120 мин, до 5 попыток) и разделение
  временного сбоя и отказа по существу: нет прав/токена/функции → статус `blocked`
  сразу, без бессмысленного долбления площадки.
- Отложенное расписание: `enqueue(..., when=...)` — пост на 19:00 не уйдёт в 10:00.
- Джоб `publish_queue` каждые 10 минут разбирает очередь; задача заводится только
  когда очередь непустая, чтобы журнал не заполнялся пустыми записями.
- `Publication` расширена полями очереди (миграция `64e59c73f0d2`); `publish_plan`
  сохраняет текст и время повтора вместо голого «failed».
- `api/routes_publish.py` — очередь, расписание, ручной повтор, отмена.
- Telegram `/queue` — состояние очереди и повтор по id; страница «Публикации» в дашборде.

### BLOCK 11 — Telegram Control Center
- `core/notify.py` — отчёт о завершившейся фоновой задаче приходит сам. Раньше о
  провале ночного джоба владелец узнавал, только если заходил в `/tasks`: снаружи
  неделя падений выглядела как «система просто ничего не постит».
- Громкость по делу: провал, ожидание согласования и отмена — сообщаем; успех
  фонового джоба молчалив, иначе настоящие проблемы тонут в потоке «всё хорошо».
  Задачи, запущенные вручную из Telegram, отвечают сами и не дублируются.
- В отчёте о провале всегда есть текст ошибки — без него чинить нечего.
- `/errors [часы]` — провалы задач и ошибки вызовов моделей одним списком;
  `GET /api/tasks/errors` (объявлен выше `/{task_id}`, иначе перехватывался им).

### BLOCK 12 — Web Dashboard
- `core/health.py` + `api/routes_health.py` — состояние системы одним агрегатом.
  Данные и раньше лежали в БД, но нигде не сводились: чтобы понять «работает ли
  всё», приходилось открывать пять страниц и Telegram.
- Статус агента опирается на факт: не вызывавшийся сутки — `silent`, а не «онлайн»;
  доля успеха ниже 80 % — `degraded`. Молчащий агент остаётся в списке, иначе
  сломанный джоб просто исчезает и картина «всё зелено» врёт.
- Планировщик отчитывается честно: `running: false`, если не поднят, а не пустой
  список молча. Джобы — со временем следующего запуска.
- Страница «Здоровье» в дашборде: вердикт, агенты, площадки, планировщик,
  задачи, расходы за день/неделю/месяц и ошибки за сутки.

### Работа без внешних ИИ (режим «только управление»)
- `ai_router.available_providers()` / `ai_available()` — система заранее знает,
  есть ли чем работать, вместо того чтобы гнать вызов и падать.
- Без единого ключа бот отвечает списком рабочих команд и адресами бесплатных
  провайдеров. Раньше приходило «All AI providers failed» — по такому тексту
  непонятно, что делать.
- `command_center` больше не заводит задачу, которая гарантированно упадёт:
  проблема не в выполнении, а в том, что выполнять нечем.
- Разделены два разных текста ошибки: «нет ни одного ключа» и «все провайдеры
  отказали» — беды разные и чинятся по-разному.
- `/diag` и «Здоровье» показывают режим: полный или только управление.

### Найдено живой проверкой на поднятом сервере
- Telegram без токена уходил в браузерный путь и возвращал «нет браузерного
  сценария»: причина подменялась, и очередь пять раз повторяла заведомо
  безнадёжную публикацию. Telegram — свой бот, браузером не подменяется;
  теперь честное «не настроена: не заданы TELEGRAM_BOT_TOKEN» и статус `blocked`.
- Отсутствие браузерного сценария и самого браузера отнесены к постоянным отказам:
  само не пройдёт, повторять нечего.

### Готовность к запуску
- **Строка подключения Supabase ложила бы деплой на первом же подключении:**
  Supabase отдаёт `?sslmode=require`, пулер добавляет `?pgbouncer=true`, а SQLAlchemy
  передаёт эти параметры прямо в `asyncpg.connect()`, который их не знает и падает
  с TypeError. `normalize_db_url` переводит `sslmode` в понятный asyncpg `ssl` и
  убирает несовместимые параметры. Шифрование при этом не теряется.
- Проверка идёт не по тексту строки, а по фактическим kwargs, которые уйдут
  в asyncpg — сверка с реальной сигнатурой `asyncpg.connect`.
- Цепочка миграций прогнана с нуля на пустой БД: все 6 ревизий применяются.

### Подключение Instagram из дашборда
- `FACEBOOK_APP_ID`, `FACEBOOK_APP_SECRET` и `NEXUS_PUBLIC_URL` не принимались
  дашбордом вообще: кнопка «Подключить» требовала их, а вписать было некуда —
  оставался только ручной путь через Graph API Explorer.
- Карточка Instagram переписана под OAuth в один клик; поля токена и Account ID
  помечены как заполняемые автоматически.
- Проверено вживую: ключи из дашборда сразу строят рабочую OAuth-ссылку
  и переживают перезапуск процесса.

### Важно про `DATABASE_URL`
Задаётся **только** в Render → Environment, дашборд для него не подходит:
подключение к БД создаётся при старте процесса, а хранить строку внутри той самой
базы, которую она включает, — замкнутый круг (на эфемерной SQLite она исчезнет
при первом же рестарте).
